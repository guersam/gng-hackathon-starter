# 「관제탑」 — 설계와 계획

Gerald Weinberg의 체험학습(experiential learning) 전통에서 영감을 받은 모바일 웹 시뮬레이션 게임.
도구는 Walk&Talk 세션(김창준) 두 편에서 가져왔다.

- **「메타포와 클린 랭귀지」** — 은유(metaphor), XP의 시스템 은유, David Grove의 **클린 랭귀지**
- **「Team Big Five」** — Eduardo Salas의 **Team Big Five** 5요소 + 3개 조정 메커니즘

원저작에 해당하는 학술 출처는 Grove의 Clean Language와 Salas et al.의 팀 효과성 모형이며,
이 저장소는 그 개념을 게임 규칙으로 옮긴 구현물이다. 세션 녹취 자체는 포함하지 않는다.

---

## 1. 한 줄 규칙

> 내 계기판을 목표대로 만드세요. 단, **내가 보는 축과 내가 만지는 축은 다르고**,
> 조작하려면 남에게 물어 **번역 토큰**을 얻어야 합니다.

4~6명 · 같은 공간 · 각자 폰 · 12~15분 + 회고.

---

## 2. Weinberg를 어떻게 따랐는가

Weinberg의 체험학습은 "강의로 알려준 뒤 연습시키기"가 아니다.
**먼저 겪게 하고, 겪은 것을 자기 손으로 해석하게 한다.** 그래서 이 게임은 이렇게 짜였다.

| Weinberg적 원칙 | 이 게임에서 |
|---|---|
| 규칙이 아니라 **구조**가 행동을 만든다 | 아무도 "소통하세요"라고 말하지 않는다. 관측·행위를 분리하니 소통 말고는 길이 없다 |
| 실패가 안전해야 한다 | 연습 라운드는 무제한이고, 여기서 돌린 것은 본 게임에 반영되지 않는다 |
| 시스템은 관찰자에 따라 달라 보인다 | 6개 은유 스킨. 같은 다이얼이 사람마다 다른 세계의 단어로 보인다 |
| 배움은 게임이 아니라 **회고**에서 온다 | 종료 화면이 본편이다. 승패는 첫 줄에서 한 번 언급하고 끝난다 |

## 3. 구조

### 시스템
숨은 다이얼 **4개**(A~D), 각각 **0~4의 5단계**. 화면에 숫자는 **한 번도** 나오지 않는다.

밑에 깔린 의미 축(참가자에게 절대 공개하지 않는다):
- A = 거칠기 · B = 채워진 정도 · C = 속도 · D = 열/장력

### 은유 스킨 6종
☕ 커피 자판기 · 🌱 정원 · 🎻 오케스트라 · 🧶 뜨개질 · 🔨 대장간 · ⛵ 돛단배

같은 축 A가 누구에겐 「원두 분쇄도」(먼지 가루 → 통원두), 누구에겐 「음색의 결」(유리 하모닉스 →
터지는 타악)이다. **120개 단어가 전부 서로 다르다.** 겹치는 단어가 하나라도 있으면 번역이 필요 없어진다.

### 역할 비대칭 — 이 게임의 심장
사람마다:
- `reads` 축 2개 — **볼 수 있지만 못 바꾼다**
- `writes` 축 2개 — **바꿀 수 있지만 결과가 안 보인다**
- `goals` — 목표를 아는 축. **반드시 내가 못 바꾸는 축이다**

구조적으로 보장되는 불변 조건:
```
reads ∩ writes = ∅        내 행동의 결과를 나는 볼 수 없다
goalAxes ∩ writes = ∅     내가 아는 목표는 내가 못 바꾼다
모든 축에 writer / reader / goal-holder가 최소 1명씩
```

→ **축 하나를 맞추려면 최소 3명이 사슬을 이룬다.** 목표 보유자 → 조작자 → 관측자.
혼자 할 수 있는 일이 하나도 없다.

### 번역 토큰과 클린 질문 4박자
축을 한 칸 돌리려면 토큰 1개. 시작 0개. 토큰을 얻는 **유일한** 방법:

1. **묻기** — 폰에서 대상·질문 유형·주제어를 고른다 → 실제 질문은 **육성으로**
2. **답하기** — 상대가 소리 내어 답한다
3. **되돌려 말하기** — 「제가 이해한 건 ___ 입니다」
4. **확인** — 맞으면 **두 사람 모두** +1 토큰. 아니면 3번으로 되돌아간다

이 네 박자는 Team Big Five의 **닫힌 루프 커뮤니케이션** 행동 지표 그대로다.

클린 질문 5종(원전 문구 그대로, 폰에 고정 문구로 박혀 있다):

| 카테고리 | 문구 |
|---|---|
| 속성 | 그 「X」는 **어떤 종류의** 「X」인가요? |
| 속성 | 그 「X」에 대해 **그 밖에 또 다른** 게 있나요? |
| 은유 | 그 「X」는 **마치 무엇 같나요**? |
| 관계 | 「X」와 「Y」 **사이에 어떤 관계**가 있나요? |
| PRO | 그러면 **어떤 일이 일어나면 좋으시겠어요**? |

> **폰은 채팅 도구가 아니라 허가증이다.** 이게 설계의 핵심이다.
> 폰으로 대화하게 만들면 방 안이 조용해지고 체험학습이 죽는다.
> 폰은 "누가 누구에게 무엇을 물을 수 있는가"만 통제하고, 말은 전부 육성으로 오간다.

### 제약이 만드는 병목
- 라운드 **90초** × 최대 5라운드 (`NEXT_PUBLIC_ROUND_MS`로 조정 가능)
- **한 사람은 동시에 하나의 루프에만** 응답자로 들어간다 → 인기 있는 사람에게 줄이 선다
- 라운드가 끝나면 **남은 토큰 전부 소멸** → 쌓아두기 불가, 지금 써야 한다
- 손대지 않은 축 **하나**가 스스로 움직인다(드리프트) → 안 본 곳이 변한다
- 라운드 종료 피드백은 **"4개 중 N개 일치"뿐**. 어느 축인지 알려주지 않는다

### 시스템 은유 — 원전의 절정
3라운드부터, 누구나 은유 하나를 제안할 수 있다. **전원이 동의하면** 그때부터
모두의 계기판과 목표 카드가 **같은 은유로 통일**된다. 번역 비용이 사라진다.

**대가: 그 순간 전원의 토큰이 0이 된다.**

XP가 시스템 은유를 실천법에 넣은 이유를 몸으로 겪게 하는 장치다.
지금 손해를 보고 공용 언어를 살 것인가, 아니면 남은 시간 내내 통역비를 낼 것인가.
대부분의 팀은 사지 않는다. 그리고 회고에서 그 사실을 마주한다.

## 4. 회고 (종료 화면 = 본편)

승패는 첫 줄에서 한 번만 말하고 넘어간다. 그 아래는 전부 **어떻게 말했는가**에 대한 것이다.

1. **소통 지도** — 누가 누구에게 물었는지 방향 그래프. 굵기=횟수, 색=루프가 닫혔는지.
   **한 번도 질문받지 못한 사람 / 한 번도 질문하지 않은 사람**을 이름으로 짚는다
2. **질문 유형 분포** — 5종 중 안 쓴 질문을 이름 불러 지적한다 (대부분 팀은 「어떤 종류의」 하나만 쓴다)
3. **닫힌 루프 성공률** — 되돌려 말했을 때 한 번에 맞은 비율
4. **공유 은유 전/후** — 분당 토큰 획득 속도 비교. 안 샀다면 그 사실을 지적한다
5. **Team Big Five 8요소 병목 추정** — 요소마다 데이터 신호 1개 + 상/중/하.
   「신호」와 「해석(추정)」을 시각적으로 분리한다. 단정하지 않는다
6. **회고 질문 3개** — 데이터에서 파생된, 클린 랭귀지 문법의 질문

원전의 마지막 제안을 그대로 옮긴 것이다:
> "8개 요소 중 어떤 게 안 되어서 병목인가를 생각해 보세요."

## 5. 루브릭 대조

| 루브릭 | 어떻게 충족하는가 |
|---|---|
| **1. W&T 도구 1개 이상 조합해야만 통과** | 토큰의 **유일한** 획득 경로가 〈클린 질문 5종〉 + 〈은유 번역〉 + 〈닫힌 루프 4박자〉의 결합이다. 토큰 없이는 다이얼이 물리적으로 안 움직인다. 3라운드부터는 〈시스템 은유〉가 네 번째 도구로 들어온다 |
| **2. 규칙은 단순, 제약이 병목을 유발** | 규칙은 한 줄. 병목은 규칙이 아니라 구조에서 나온다 — 관측·행위 분리, 1인 1루프, 90초, 토큰 소멸, 드리프트, N/4 피드백 |
| **3. 승패 너머 되돌아볼 거리** | 종료 화면 6개 섹션 전부가 상호작용 패턴에 관한 것이다. 모든 이벤트가 append-only 로그로 남아 회고의 원재료가 된다 |
| **4. 진행요원 없이 5분 내 이해** | 온보딩 3장(약 60초) + **무제한 연습 라운드**. 화면이 직접 유도한다 — 토큰 0개일 때 조작 버튼이 비활성이고, 버튼 문구가 「질문 열기 (토큰 얻기)」다. 연습에서 돌린 것은 본 게임에 반영되지 않아 안전하게 실패할 수 있다 |

## 6. 기술

- Next.js 15 App Router / React 19 / TypeScript / 순수 CSS / 외부 UI·차트 라이브러리 0개
- **상태 = append-only 이벤트 로그 폴딩.** 서버에 가변 상태가 없다.
  같은 로그가 게임 진행과 회고 데이터 양쪽을 만든다
- 저장소: Upstash Redis LIST + Lua CAS(`LLEN` 비교)로 원자적 append. 없으면 인메모리 폴백
- 동기화: 1초 폴링. WebSocket 없음 (워크숍 와이파이에서 더 잘 버틴다)
- **정보 비대칭은 서버가 강제한다.** 클라이언트로 나가는 응답에서 남의 목표, 못 읽는 축의 값,
  정답 상태를 아예 지운다(`redactState`). 개발자 도구를 열어도 답이 안 보인다.
  게임이 끝나면 전부 공개한다 — 회고하려면 답을 봐야 하므로

## 7. 진행 안내 (진행요원용 — 없어도 되지만 있으면 좋은 것)

1. 4~6명이 한 방에 모인다. 한 명이 「새 방 만들기」 → 4글자 코드를 보여준다
2. 나머지는 각자 폰에서 코드 입력 → 이름 입력 → 참가
3. 아무나 「시작하기」. 이후 진행요원이 할 말은 **없다**
4. 게임이 끝나면 **각자 자기 폰의 회고 화면을 보면서** 이야기한다.
   화면이 던지는 질문 3개로 시작하면 된다
5. 한 판 15분 + 회고 15~20분

**진행요원이 하면 안 되는 것:** 은유 사이의 대응 관계를 알려주는 것.
그 번역을 스스로 해내는 과정이 이 게임의 전부다.

## 8. 알려진 한계

- 한 기기에서 두 명이 플레이할 수 없다(브라우저 localStorage로 플레이어를 식별한다). 1인 1기기.
- 게임이 시작된 뒤에는 중간 합류가 안 된다. 다음 판에 들어와야 한다.
- 방 데이터는 12시간 뒤 만료된다. 회고를 오래 남기려면 화면을 캡처해 두어야 한다.
- 3인도 플레이 가능하지만 병목이 약하다. **4~6인**을 권한다.
