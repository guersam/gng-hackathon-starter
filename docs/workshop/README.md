# 7팀 × 90분 체험형 게임 해커톤

전제는 팀마다 AI로 코딩하는 사람은 한 명일 수 있다는 것이다. 그래서 코딩을 팀 활동의 중심에 두지 않는다. 팀은 첫 8분 안에 기준 게임을 하고, 코더가 작업하는 동안 나머지 구성원은 실제 참가자·규칙 편집자·관찰자로 계속 다음 플레이를 준비한다.

## 한 팀의 네 작업 패킷

역할을 강제하지는 않지만 네 결과물은 동시에 진행한다.

- 경험 패킷: 60초 안에 읽을 상황, 참가자가 실제로 할 행동, 끝난 뒤 남길 한 장면
- 규칙 패킷: 상태·행동·결과를 각 한 문장으로 쓰고 금지할 행동 하나를 정한다
- 플레이 패킷: 휴대전화 2대 이상으로 매 5분 빌드를 플레이하고 막힌 문구·입력·순서를 적는다
- 피날레 패킷: 30명이 두 방에서 접속할 때 필요한 링크, 1분 설명, 종료 신호와 실패 시 복구법

코더는 네 패킷을 한 번에 구현하지 않는다. 팀은 두 기준 게임 중 가까운 하나를 고르고, 기존 게임을 직접 개조할지 복사해 새 팩으로 보존할지 결정한다. 먼저 상태·행동·결과 한 고리만 바꿔 다시 플레이하고 관찰된 실패 하나씩만 다음 슬라이스에 넣는다. 두 경로는 [기준 게임에서 내 게임 시작하기](../games/modify-a-game.md)를 따른다.

## 90분 진행표

| 시간 | 전원이 하는 일 | 코더의 얇은 슬라이스 | 확인 가능한 산출물 |
|---|---|---|---|
| 0–8 | `/yoil` 또는 `/handoff` 기준 게임을 실제 플레이 | 배포·브랜치 확인 | 전원이 한 번 행동함 |
| 8–15 | “무엇을 알게 만들 것인가”와 금지할 교훈을 결정 | 기준 게임 직접 개조 또는 Handoff 팩 복사 | 60초 경험 설명 |
| 15–23 | 종이/말로 규칙 enactment | 상황·선택·공개만 구현 | 클릭 가능한 첫 판 |
| 23–32 | 전원이 첫 판 플레이, 관찰 하나 기록 | 가장 큰 막힘 하나 수정 | 휴대전화 플레이 링크 |
| 32–45 | 5분마다 플레이→관찰→한 수정 반복 | 상태/행동/결과 중 하나씩 확장 | 후보 게임 + 30명 계획 |
| 45–60 | 외부 배정표로 다른 두 팀 게임 플레이 | 치명 오류만 고침 | 팀당 타팀 증거 2개 |
| 60–68 | 외부 폼에 투표: 재미가 아니라 의도한 경험이 실제로 일어났나 | 배포 고정 | 근거가 붙은 후보 순위 |
| 68–76 | 우승 팀 설명·링크를 두 방에 배포, 전원 입장 | 접속 실패 복구 | 30명 준비 상태 |
| 76–86 | 두 방 30명 플레이 | 로그만 관찰 | 완료 또는 명시적 실패 기록 |
| 86–90 | 실제 행동 한 장면과 다음 실험 공유 | 변경 없음 | 우승 게임 증거와 재개방 조건 |

갤러리·배정·투표는 외부 문서/폼이 맡는다. 후보 게임은 자체 팀이나 실시간 서버를 가질 필요가 없지만 manifest의 `finalePlan`에 30명이 어떻게 참여할지 반드시 쓴다: 같은 URL, 방별 URL, 순차 턴, 진행자 공개 중 하나다.

## 후보의 최소 완료 조건

1. 링크를 연 사람이 60초 안에 무엇을 할지 안다.
2. 네 사람이 한 번 이상 입력하고 결과 공개까지 간다.
3. 코드를 새로 받는 팀이 `pnpm check:game`으로 규칙 검사를 실행한다.
4. 30명·두 방에서 누가 링크를 나누고 언제 시작/종료하는지 문서에 있다.
5. 투표 문항은 “재미있었나”가 아니라 “의도한 경험을 보여 준 관찰 가능한 행동은 무엇이었나”다.

Handoff Lab은 Gerald M. Weinberg의 공개된 “Tinkering With Toys” 메커니즘에서 영감을 받은 독자적 예제다. 원문 지침이나 물리 자료를 복제하지 않는다.
